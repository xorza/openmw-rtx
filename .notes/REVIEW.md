## Memory requests leave the design's promise to the library's defaults

- [ ] **A dedicated essential allocation gets priority 0.0, below content's 0.25** — `components/rtxvulkan/device/memory/memory.cpp:50-58`, `components/rtxvulkan/device/memory/memory.cpp:202-226`, `components/rtxvulkan/device/memory/memory.cpp:45-48`, VMA `build-asan/components/rtxvulkan/fetched/vma/include/vk_mem_alloc.h:13889-13907` and `build-asan/components/rtxvulkan/fetched/vma/include/vk_mem_alloc.h:13911-13990`. `askingFor` value-initialises `VmaAllocationCreateInfo`, so `priority` is `0.0f`. `take` (the essential path) never sets it. VMA ignores `priority` for an allocation it suballocates from a default pool, which gets 0.5. It passes `finalCreateInfo.priority` straight to `AllocateDedicatedMemory` for every dedicated allocation. VMA makes an allocation dedicated when it is larger than half the 64 MiB block, and `vmaAllocateMemoryForImage` also does so when the driver reports `prefersDedicatedAllocation`. Render targets meet both conditions: an `rgba16f` target at 7680x2160 is 132 MB. With `VK_EXT_memory_priority` enabled (NVIDIA and RADV both expose it), the G-buffer, the histories and the upscaler targets therefore carry priority 0.0. Content carries 0.25 (`sContentPriority`). A driver that evicts under pressure moves the frame's targets out first. That is the opposite of what `MemoryUse` and the `MemoryPriority` option promise (`components/rtxvulkan/device/requirements.cpp:122-126`, `components/rtxvulkan/device/memory/memory.hpp:116-118`). The comment at `components/rtxvulkan/device/memory/memory.cpp:45-47` ("below the half the library gives every block outside a pool, which is where what the frame holds is made") is true only of the suballocated half. Better: name an `sEssentialPriority` (0.5, VMA's default-pool value, or 1.0) beside `sContentPriority`, and set it in `take` for both the buffer and the image overloads. One `askingFor(properties, use)` then states the priority of every allocation. Extend `memory.cpp`'s GPU test: allocate an essential image larger than half a block and assert `VmaAllocationInfo`'s dedicated status and the priority it was given. *(severity: high; benefit: under pressure the frame's own memory is evicted last, as designed)*
- [ ] **`Staging` says "host memory, write-combined" and asks only for host-visible coherent** — `components/rtxvulkan/device/memory/buffer.cpp:21-37`, `components/rtxvulkan/device/memory/buffer.hpp:40-45`, `components/rtxvulkan/device/memory/memory.cpp:50-58`, `components/rtxvulkan/device/memory/memory.cpp:158-162`, VMA `FindMemoryTypeIndex` (`build-asan/components/rtxvulkan/fetched/vma/include/vk_mem_alloc.h:14271-14326`). `askingFor` sets `requiredFlags` and nothing else, so VMA's cost is zero for the first matching type and it returns that type. `Staging` (`HOST_VISIBLE|HOST_COHERENT`) gets system write-combined memory only because NVIDIA, AMD and RADV list that type before the BAR type and the cached type. On a driver that lists `DEVICE_LOCAL|HOST_VISIBLE|HOST_COHERENT` first, every staging block lands in the BAR heap, which on a card without resizable BAR is 246 MiB that `HostWritten` tables need. The same applies to `DeviceLocal` and `mVideoType`, which take the first `DEVICE_LOCAL` type and could pick the BAR type. Better: in the `MemoryAllocator` constructor, compute one `memoryTypeBits` mask per `BufferKind` from the device's types: staging is host-visible, coherent, not device-local and not cached; device-local is device-local and not host-visible where such a type exists. Pass the mask in `VmaAllocationCreateInfo::memoryTypeBits`. Pull the choice into a pure function and test it on the RTX 2060, Ada and RADV type lists. *(severity: low; benefit: the kind's promise is stated in the request, not borrowed from driver order)*
- [ ] **The "foreign" card fixture is NVIDIA's memory layout under AMD's driver id** — `apps/components_tests/rtxvulkan/device/physicaldevice.cpp:222-228`, `components/rtxvulkan/device/memory/memory.cpp:164-186`. The case that stands for "a Radeon or an Arc" changes only `driverID`. RADV's and AMD's memory type lists, including the `DEVICE_COHERENT_AMD` types that `MemoryAllocator` must skip ("a pool asked of each stopped those cards at start-up"), appear in no fixture. The pool and video-type choice is reachable only with a live device, and no AMD device runs here. Better: add a `describeRdna2` fixture from a Vulkan Hardware Database report. Move the pool and type selection out of the `MemoryAllocator` constructor into a pure function over `VkPhysicalDeviceMemoryProperties`, and test it on the three fixtures. *(severity: low; benefit: the AMD path is held by a test on a machine with no AMD card)*

## Shading math departs from the exact form it claims

- [ ] **The refracted ray's cone is twice too wide from above and 1.5 times too wide from below** — `components/rtxvulkan/shaders/lib/water.glsl:324`, `components/rtxvulkan/shaders/lib/water.glsl:327`, `components/rtxvulkan/shaders/lib/sea.glsl:29`, `components/rtx/shaders/brdf.h:180`. `lobe` is `ggxConeWidth(roughness², …)`. `brdf.h` defines that as the reflected cone, "twice the half vector's angle, on each side of the mirror direction": a facet tilt of θ deflects a reflection by 2θ. A refraction from air into water deflects by `(1 - 1/n)·θ`, which is `WATER_REFRACTION_BEND·θ`. So the refracted cone is `lobe · WATER_REFRACTION_BEND / 2` (×0.125), not `lobe · WATER_REFRACTION_BEND` (×0.25). From below the water the deflection is `(n - 1)·θ`, so the factor is `(WATER_IOR - 1) / 2` (×0.167), and the code still takes ×0.25. The comment says refraction "bends by a third of what reflection does", which is neither case. The bed seen through water reads its textures a mip level coarser than its slopes justify, and the sky through Snell's window blurs half as much again. Fix: pass `lobe * 0.5 * (fromBelow ? WATER_IOR - 1.0 : WATER_REFRACTION_BEND)`, or define the two bends beside `WATER_REFRACTION_BEND`, and correct the comment. `caustic`'s `blurred` (`components/rtxvulkan/shaders/lib/sea.glsl:315`) refracts the sun once and keeps the bend whole, which is right. *(severity: medium; benefit: correct blur behind every water surface)*
- [ ] **`additiveAlong` claims the rasterizer's sum and computes a product of two means** — `components/rtxvulkan/shaders/lib/medium.glsl:227-230`, `components/rtxvulkan/shaders/lib/medium.glsl:348-352`. The doc says the result is "`texel * tint * alpha * (light + glow)` summed over the crossings". The code sums `texel·tint·α` and `glow·α` apart, then returns `Σ(texel·tint·α) · (L + E·Σ(glow·α)/Σα)`. That equals the stated sum only when every crossing has the same glow. An effect sheet with a glow over an ice wall without one spreads the glow onto the wall's texels, and the sheet's own glow loses its texture. Fix: accumulate `mGlowed += sharePart(texel.rgb · tint · glow · α)` and return `(vec3(mUnlit)·L + vec3(mGlowed)·E) / SHARE_UNIT`. The divide by `mCoverage` goes away. *(severity: medium; benefit: exact additive glow, one divide fewer)*

- [ ] **`GrowableBuffer::outgrow` and `SlotTable::sync` remake and refill a whole table on the frame the doubling trips** — `components/rtxvulkan/device/memory/growablebuffer.hpp:38-40`, `components/rtxvulkan/device/memory/growablebuffer.cpp:19-25`, `components/rtxvulkan/device/memory/slottable.hpp:99-103`, `components/rtxvulkan/device/memory/slottable.hpp:70`. - [ ] **A posed body is built whole only once it passes `sRebuildEvery` placements, so frames alternate between a rebuild and none** — `components/rtxvulkan/scene/sceneacceleration.cpp:174-197`, `components/rtxvulkan/scene/sceneacceleration.hpp:131-134`. `prepareRefit` rebuilds the oldest posed mesh only where `mPlacements - builtAt >= 64`.
